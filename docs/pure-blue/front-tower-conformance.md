### C2 — memory rows

- **Today.** A counting allocator (`crates/blue-lang-runtime/src/alloc.rs`: `retained()` :62,
  `charged_to` :248; tests `memory_bound.rs`, `alloc_count.rs`). No resource handles beyond
  `tcp_connect`; no cell; `send` copies.
- **Change.** Expectation kinds `leaks(0)` and `closes_at(...)` in `rows.rs`, on walker and VM.
- **First commit.** `leaks(0)` over `retained()`, with one row.
- **Exit.** I2, I3, I4 per runtime.
- **First slice landed.** `leaks(N)` on the walker and the VM, three rows in
  `spec/rows/memory.b` at `leaks(0)`.
- **`closes_at(:end)` landed (2026-11-21).** `blue_lang_runtime::handles` counts the host handles a thread holds open (TCP connections, listeners, serial ports), each from the word that opens it until `tcp_close` or its last drop, once. A `closes_at(:end)` row runs on the walker and the VM and passes when the count returns to where it began; three rows in `spec/rows/memory.b` (a listener left open, a pair closed by hand, an accepted connection left open). Red-run: with a drop not counted as a close, the two left-open rows fail on both evaluators (open 1, open 3). Next: points inside a run (`closes_at` at a named step), the HTTP listener (landed with its own row), NATS, Postgres and RESP (counted, held by a test each in `checks.network`'s peer suites: closed by hand and left open both return the count), the wire (UDP, counted until `flash_close`/`tide_close` closes its last channel or its last reference drops; two rows), then the display and kernel fds, which need a display and Linux BPF; move vs copy is R5's.
- **Move vs copy is R5's, measured (2026-11-21).** In the Rust runtime every `send` and `spawn` deep-copies its data (`blue_lang_proc::mailbox::deep_copy`: containers rebuilt, scalars and strings shared, closures and host handles refused with "a message is copied to the receiver, and a host handle is not data", probed with a cell). Since every data value is immutable, sharing and copying are indistinguishable to a program, so a move-vs-copy row has nothing to observe until processes own their heaps: it is a property of R2's per-process heaps and R5's mailboxes, and its rows (a message sent at its last use moves, one read again is copied, by allocation per heap) land with R5, after R4.
- **Measured (2026-11-18), the next slice's input.** `leaks` run over the first 190 value
  rows on the walker: 177 leave 0 bytes. Eleven `dispatch.*` rows leave about 11 KB per run,
  `fn.memoize` 14.8 KB and `host.temp_dir` 562 bytes. Whether that is a cache on the
  harness's shared `Env` or a leak in the evaluator is not yet known. The sweep stalled on a
  host row that reads stdin. So the I3 gate must skip such rows, and it must run in a release
  build: a debug sweep took about 2 hours for 190 rows.
- **Measured (2026-11-20): cycle-through-cell is the VM's letrec.** `control.while` leaks only on the VM, and so does `while(i < 0, 1)`, whose body never runs (13 KB per run; `set!` alone leaks nothing). `while` is tatara's macro over `(letrec ((loop (lambda () …))) (loop))`, and the VM lowers `letrec` to `(let ((loop nil)) (set! loop …) …)` with closures that capture by cell (`tatara-lisp-eval/src/vm/compile.rs`, `desugar_letrec`). The loop lambda captures the cell that holds it, so when the scope ends the cell and the closure hold each other. Clearing the cells at scope exit would break a `letrec` that returns its own function; the fix proves the ring closed first (the cell held only by its slot and its own closure's captures, the closure held only by the cell), the way `release_if_closed` proves a frame closed, and only then sets the cell to nil. It belongs in tatara's VM and ships in a tatara release. The same shape (named recursion through a cell) is the first suspect for `lisp.defstrategy`, `lisp.defvisitor` and the process and wire rows on the ledger.
- **Fixed (2026-11-20, tatara 0.4.25):** the VM letrec ring; `control.while` left the ledger. **Measured next: a ring through a list.** `lisp.defstrategy` and `lisp.defvisitor` leak about 16 KB per run on the walker and the VM alike. `defstrategy` expands to `(define s (make-strategy kvs...))`, and `make-strategy` returns a lambda over `handlers`, the `&rest` list of handler closures, which capture the globals that bind `s`. That is the closure-argument ring tatara-lisp-eval 0.4.24 releases, except the closures sit inside a list, and `handles_to_frame` counts a `Value::List` as zero on purpose: an `imbl::Vector` shares tree nodes between lists, so a closure with strong count 1 can still be reachable from two lists, and walking one would over-count and clear a frame still in use. `imbl` 7 exposes no test for unshared nodes. The fix is a tatara design step: either a list representation whose sole ownership is provable (a list held by one `Arc` and built inline, as `&rest` arguments are), or rest arguments bound as such a list, then the release walk follows a list only when that proof holds. The process and wire rows (55-95 KB) are the next to measure.
- **Measured (2026-11-20): the process leak needs the worker pool.** Probe rows on the walker and the VM: a server spawned, sent to and left running leaks 0 B; `self` alone and `send(self, 7); receive()` leak 0 B; a spawned server plus the main program blocking in `receive()` leaks 63,960 B, the ledger's `processes.spawn_server` figure. Blocking main while another process is runnable is what starts the node's scheduler pool (`Node::pool`, `crates/blue-lang-proc/src/node.rs`: `blue-scheduler-N` threads holding `me`, the work queue and `radio`, which end only when the work channel's sender, held by the node, is dropped). So the question for the fix is what keeps the node, or a process parked by a pool thread, alive after the run: a strong `me`, a process the pool still holds, or the channel. Read `schedule` and the node's drop path next; the fix is the node ending its pool and its processes when its program ends.
- **Measured further (2026-11-20).** The default node has one scheduler, so no pool runs; the leak is narrower than that. Plain `spawn` children leak nothing, even one that sends to the waiting root; a `spawn_server` the root drives with `receive()` leaks 60,940 B, and the same server never driven leaks nothing. A `Node::release` that drops the run queue, the state (mailboxes, server info, pending), the lanes and the undelivered flights, registered on the root interpreter's `on_release`, changed nothing (60,940 B still): so either that hook does not fire on the run's interpreter under `run_framed_accounted` (forks get their own node through `attach_node`), or what is retained lives outside the node's tables. Next: count whether the hook fires there, then look at what a driven server allocates that nothing owns (its compiled `SERVER_LOOP` chunk, the proto interpreter, a thread-local the scheduler keeps). The experiment was not landed.
- **Measured (2026-11-20, probe prints).** Under `blue run` the root's release hook fires, and the node is dropped at the end of the run with the release and without it. So the node is not what stays: the 60,940 B a driven server leaves are held outside it. Next: what a driven server allocates that outlives the node (a cache keyed per program, the compiled `SERVER_LOOP` chunk, a thread-local of the scheduler or the VM), found by bisecting the server's first slice.
- **Measured (2026-11-20): it is real memory, not the counter.** Peak RSS over 1,000 in-process runs (`run_in_surface`, release build): a plain child that sends to the waiting root grows 0.4 MB (noise), a server never driven 0, a server the root drives with `receive()` 80 MB, about 80 KB a run. So a long-lived host (the language server, `blue serve`) that runs programs with servers grows by that much each run. Ruled out: the node (dropped every run), the symbol interner (42 entries, flat), the scheduler pool (one scheduler by default). The cause is in a driven server's slice: the dispatch path (`slice_held`, `dispatch_held`, the `%state` it defines) or the server loop it compiles.
  Split further: a plain child that echoes a reply grows 0.15 MB over 1,000 runs (noise), and a child left waiting after its reply grows 0, so message passing and a waiting process are clean; the growth is `spawn_server`'s own path (its loop, `dispatch_held`, the `%state` each slice defines).
  And narrower: a server that is started and runs only its first slice (main waits on another child, so the server parks in `%server_next` with no message) grows 79 MB over 1,000 runs, the same as one that handles a message; a plain child running the same mutually recursive receive loop with the root's functions grows 0.26 MB. So the cost is a server's first slice itself. What only a server has there is code defined inside its own process interpreter (`%handler`, `%serve`, `%serve_step`, the `%state` binding, from `server()` in `node.rs`), a fork of the node's proto: the lead was whether those definitions' rings are released when the process is dropped while parked.
  Not that alone: a child spawned from a named function (its definition compiled into the process) and parked in `receive()` grows 0.2 MB over 1,000 runs, an anonymous one 0.1 MB, both noise. What is left is the server's own: the `%state` binding `server()` makes and `%serve_step` sets each step, and the node's `Kind::Server` bookkeeping (`Info::kept`, `armed`, `dispatch_from`). Next: instrument `server()` and the server arm of the dispatch in `node.rs`, taking each piece out in turn under the RSS probe (1,000 `run_in_surface` runs, peak RSS).
