# DOCUMENTATION — every blue project documents itself, and the language has a book

D0 to D4.1 and D8 are built. D5, D6 and D9 are not built. D7 is in progress.
The [Ledger](#8-ledger) gives the state of each step.

## 1. Destination

Documentation is a battery like any other. A blue project, whatever its
morphology (a bidama, a program, a service, a controller, an action), gets with
no configuration: a reference generated from its `@moduledoc` and `@doc`
attributes, whose examples run as tests; a book rendered from its prose pages
and that reference; a README, an `AGENTS.md` and an `llms.txt` rendered from
the same sources; and a site published by the CI sentence. Nothing is written
twice, no example can drift from the code, and every rendering is gated fresh.
Blue itself is the first consumer: the **Blue Book** is to blue what *The Rust
Programming Language* is to Rust, generated by the same machinery.

## 2. Standards adopted

| Standard | What we take | Where it lands |
|---|---|---|
| Diátaxis (tutorial, how-to, reference, explanation) | every prose page is exactly one of the four, declared in its front matter; a page that mixes two is split | the book's structure; a check refuses a page with no `kind` |
| AGENTS.md (Linux Foundation AAIF; plain Markdown at the root, nearest file wins) | one agent file per project, rendered, never hand-maintained; `CLAUDE.md` is the same rendering | root and per-directory where a subtree has its own rules |
| llms.txt (H1, a summary blockquote, H2 sections of links with one-line descriptions) and `llms-full.txt` (the expanded companion, a convention) | both rendered from the book's table of contents and the reference | the project root and the published site |
| Rust's model: rustdoc plus mdBook plus doctests | the reference is generated from code attributes, the book from chapters, and every code block in either is executed by `blue test` | `hon` (§5) |

## 3. Sources, one per fact

| Fact | Its one source | Rendered into |
|---|---|---|
| what a definition does, with an example | `@doc` (typed, doctested; B0056–B0060) | reference, `blue doc`, editor hover, llms-full |
| what a package or module is for | `@moduledoc` (first line is the purpose) | reference, book chapter heading, CATALOG, README summary |
| what a project is and how it is built | the Bluefile (`package`, `service`, `access`, `packages`) | README header and quickstart, AGENTS.md build section |
| how to learn it, do a task with it, or why it is shaped so | `docs/**/*.md` with front matter `kind:` | the book |
| rules for agents working in the repo | `docs/agents.md` (one prose page, kind `reference`) plus the Bluefile facts | AGENTS.md / CLAUDE.md |
| runnable examples | doctests and `examples/` programs | every rendering that shows code; each one runs in `blue test` |

## 4. The renderings

| Rendering | Contents | Gate |
|---|---|---|
| reference | every public definition by package: signature, doc line, examples, blueshift rung, laws when stated | `-fresh`; B0056 counts each definition without `@doc` and the census holds that count to its ratchet, so a new undocumented definition fails while the old ones wait to be documented |
| book | chapters in Diátaxis order (tutorial, how-to, reference, explanation), search, cross-links to the reference | `-fresh`; every code block executed |
| README.md | name, one-paragraph purpose (from `@moduledoc`), quickstart (from the first tutorial), the introduction's sections with their facts rendered (§5), links into the book with the explanation folded | `-fresh`; the `generated-tree` hook refuses a hand edit |
| AGENTS.md, CLAUDE.md | build and test commands from the Bluefile, the agent rules page, pointers into the book | `-fresh` |
| llms.txt, llms-full.txt | the book's table of contents with one-line descriptions; the full text | `-fresh` |
| site | the book as static HTML, rendered by blue's frontend framework, published by `blue-project.yml` | the CI sentence |

## 5. `hon` (本) — the renderer

A bidama, so every blue project reaches it: it reads the Bluefile, the
attributes (through `mokuroku`, which already reads `@doc`) and the prose
pages, and returns the renderings of §4 as values; a Bluefile word
`book("docs")` turns it on, and with no word a project still gets the reference,
README, AGENTS.md and llms files. Static HTML is produced by a blue program,
not a Rust or JavaScript static-site tool.

As built, front matter names `kind`, an optional `summary` (the one-line
description every map and `llms.txt` shows), `order` (a page's place within its
kind), `role` (`introduction` feeds the README lead, `agents` feeds AGENTS.md and
CLAUDE.md, `book` marks the rendered book) and `runs: true` (run the blocks of a
page that is not a tutorial or how-to). The `docs` check runs, in a fresh
directory per page: a block with `file=PATH` is written there; a `blue` block
without one runs (`blue test` when it holds a test); a `console` block runs each
`$` line, a leading `blue` being the blue under test, and compares the lines
shown under it; `console fails` must fail and print each shown line;
`console host` needs the network or nix and is shown, not run. Today the host
blocks are the install command, `nix flake check` and blue's own build.

A page also holds **facts**: a fenced block whose info string is `hon`, whose
first line names what to render in its place, in every rendering that shows
the page. `commands` is the table of every command `blue reference` lists,
read from the argument parser `blue` runs; `language` is the language's size
from the same reference; `packages` is the project's catalogue, each package
with the purpose its `@moduledoc` states; `include page.md#anchor` is one
section of another page, its links rewritten. The `docs` check refuses an
unknown fact, a missing page or a missing section, each by page, and renders
the rest. A `packages` fact that cannot see the package roots refuses rather
than count none, so a `generate` must list `bidamas` in its inputs. The
README's commands, numbers, standard library and gaps are facts, so none of
them is written by hand. Why facts become nodes of a typed Markdown tree:
[`MARKDOWN.md`](MARKDOWN.md).

## 6. The Blue Book

| Part (Diátaxis) | Chapters | From |
|---|---|---|
| Tutorial | install; a first script; a first program; a first bidama; a first service (from `ola-mundo`) | new pages, each a runnable sequence |
| How-to | write a test and a doctest; climb the blueshift; declare a service's access; write an action; publish a bidama | new pages, plus `ola-mundo`'s morphology examples |
| Reference | the language (forms, operators, canonical spellings), the builtins, every bidama, the diagnostics (B-codes) | generated: REFERENCE.md, CANONICAL-FORMS.md, CATALOG.md, DIAGNOSTICS.md, `blue explain` |
| Explanation | why blue, the blueshift, one spelling per meaning, gathering is host and judging is blue, the build stack, access and supervision | today's design docs, moved into the explanation quadrant with their status lines kept |

## 7. Decisions

| Question | Chosen | Rejected, and why |
|---|---|---|
| Book tool | `hon`, a bidama | **mdBook**: a second toolchain beside blue and Rust's; its code blocks cannot be run by `blue test` |
| AGENTS.md vs CLAUDE.md | one rendering, both files | **hand-written CLAUDE.md**: drifts from the Bluefile; **a symlink only**: not every checkout keeps symlinks |
| Structure | Diátaxis, enforced by front matter | **free-form docs/**: 30 pages today, mixed quadrants |
| Examples | doctests and runnable chapters only | **illustrative snippets**: the first thing to rot |
